## 1. 先建立概念：后端是什么？它和 Agent 引擎是什么关系？

### 1.1 一句话理解

```
浏览器/前端 ──HTTP请求──→ 后端(FastAPI) ──调用──→ Agent引擎(LangGraph)
   │                          │                        │
   │                          │                        │
   └──HTTP响应 ←──────────────┘                        │
         (JSON格式)              │                      │
                                 │    "帮我分析000002"   │
                                 └──────────────────────┘
```

**后端就是"中间人"**：前端不会直接调用 Agent 引擎。前端发一个 HTTP 请求给后端，后端解析请求、调用 Agent 引擎做分析、拿到结果后打包成 JSON 返回给前端。

### 1.2 这个项目用的技术

| 技术 | 干什么的 |
|---|---|
| **FastAPI** | Python 的 Web 框架 — 定义"什么 URL 触发什么代码" |
| **MongoDB** | 文档数据库 — 存股票数据、用户配置、分析结果 |
| **Redis** | 内存缓存 — 存临时数据（任务队列、限流计数器、热点数据） |
| **APScheduler** | 定时任务 — 每天定时同步股票数据 |
| **WebSocket / SSE** | 实时推送 — 前端不用轮询，后端主动推送分析进度 |


## 3. 一个请求的一生：从浏览器到 Agent 引擎再回来

假设用户在 Web UI 上点了"分析 000002"，这一路发生了什么。

### 3.1 前端发了什么

```http
POST /api/analysis/single
Content-Type: application/json
Authorization: Bearer eyJhbGciOi...（JWT Token）

{
  "symbol": "000002",
  "trade_date": "2025-07-08"
}
```

### 3.2 请求经过的每一层

```
请求到达 :8000
    │
    ▼
┌──────────────────────────────────────────────────────┐
│ 第 1 层：RequestID 中间件                              │
│ 给这个请求生成一个 UUID（如 a1b2c3d4）                  │
│ 之后所有日志都会带上这个 ID，方便排查问题               │
└──────────────────────────────────────────────────────┘
    │
    ▼
┌──────────────────────────────────────────────────────┐
│ 第 2 层：CORS 中间件                                   │
│ 检查请求来源是否在允许的名单里                          │
│ 允许的来源: localhost:3000, 127.0.0.1:3000           │
└──────────────────────────────────────────────────────┘
    │
    ▼
┌──────────────────────────────────────────────────────┐
│ 第 3 层：请求日志中间件                                 │
│ 记录: POST /api/analysis/single - 开始处理             │
└──────────────────────────────────────────────────────┘
    │
    ▼
┌──────────────────────────────────────────────────────┐
│ 第 4 层：限流中间件                                    │
│ Redis INCR "rate_limit:user_123:/api/analysis/single"│
│ 如果这一分钟已经 10 次了 → 返回 429 "请求过于频繁"      │
└──────────────────────────────────────────────────────┘
    │
    ▼
┌──────────────────────────────────────────────────────┐
│ 第 5 层：配额中间件                                    │
│ Redis INCR "daily_quota:user_123:2025-07-08"         │
│ 如果今天已经 1000 次了 → 返回 429 "今日配额已用完"      │
└──────────────────────────────────────────────────────┘
    │
    ▼
┌──────────────────────────────────────────────────────┐
│ 第 6 层：操作日志中间件                                 │
│ 记录: 用户 admin 在 2025-07-08 15:30 提交了单股分析     │
│ 写入 MongoDB 的 operation_logs 集合                   │
└──────────────────────────────────────────────────────┘
    │
    ▼
┌──────────────────────────────────────────────────────┐
│ 第 7 层：analysis 路由处理器                           │
│ app/routers/analysis.py 中的 single_analysis 函数      │
│                                                      │
│ 做的事情:                                             │
│ ① 解析请求 body → {"symbol": "000002", ...}           │
│ ② 创建一个分析任务，生成 task_id                       │
│ ③ 把任务放进 Redis 队列（LPUSH）                       │
│ ④ 立即返回 {"task_id": "abc", "status": "queued"}     │
│    （注意：不是等分析完成才返回！）                      │
└──────────────────────────────────────────────────────┘
    │
    ▼
    响应返回给前端: {"task_id": "abc123", "status": "queued"}

    ※ 注意: 路由处理器不做真正的分析，只是"提交任务"
```

### 3.3 真正的分析在哪里执行？

```
                              路由处理器把任务放进队列后就返回了
                                         │
                                         ▼
                              ┌─────────────────────┐
                              │   Redis 队列         │
                              │   queue:analysis     │
                              │   [task2, task1]     │
                              └──────────┬──────────┘
                                         │
                              Worker 在后台不断监听
                                         │
                                         ▼
┌────────────────────────────────────────────────────────────────┐
│ Worker (app/worker.py)                                          │
│                                                                 │
│ while True:                                                     │
│     task = redis.brpop("queue:analysis")  # 阻塞等待任务         │
│                                                                 │
│     # 拿到任务后：                                               │
│     ① 把任务状态改成 "running"（写入 MongoDB）                    │
│     ② 调用 FinAgentLabGraph.propagate("000002", "2025-07-08") │
│        ↓                                                        │
│        这就是你 Day 2-7 学过的 Agent 引擎！                      │
│        ↓                                                        │
│     ③ Agent 分析过程中，每完成一个节点就通过 WebSocket 推送进度   │
│        "📊 市场分析师" → "🐂 看涨研究员" → "💼 交易员决策" → ... │
│     ④ 分析完成后，结果写入 MongoDB                               │
│     ⑤ 任务状态改成 "completed"                                  │
└────────────────────────────────────────────────────────────────┘
```

### 3.4 前端怎么知道分析完成了？

```
方式一：WebSocket（推荐）
─────────────────────────
前端在提交任务后，建立 WebSocket 连接
Worker 每完成一个 Agent 节点，就通过 WebSocket 推送消息到前端
前端实时显示："📊 市场分析师完成" → "💼 基本面分析师完成" → ...


方式二：轮询
─────────────────────────
前端每隔几秒发 GET /api/analysis/task/{task_id}
查询任务状态
```

## 5. 中间件：请求的"安检通道"

### 5.1 中间件是什么

```
没有中间件：
  请求 → 路由处理器 → 响应

有中间件（洋葱模型）：
  请求 → [安检1] → [安检2] → [安检3] → 路由处理器 → [安检3] → [安检2] → [安检1] → 响应
```

每个"安检"就是一段代码，可以在请求到达路由之前做检查（比如验证身份），也可以在响应返回之前做处理（比如添加响应头）。

### 5.2 项目中有哪些中间件

| 中间件 | 干什么 | 不通过会怎样 |
|---|---|---|
| **RequestID** | 给每个请求打上唯一编号，日志可追踪 | 不会拦截，只是打标记 |
| **CORS** | 只允许来自特定地址（如前端页面）的请求 | 返回 403 禁止访问 |
| **请求日志** | 记录每个请求的方法、路径、耗时 | 不会拦截，只是记录 |
| **RateLimit** | 限制每个用户每分钟请求次数 | 返回 429 "请求过于频繁" |
| **Quota** | 限制每个用户每天总请求次数 | 返回 429 "今日配额已用完" |
| **操作日志** | 记录用户做了什么操作（如提交分析、修改配置） | 不会拦截，只是记录 |

### 5.3 限流的原理（RateLimit）

```
用户 admin 第 1 次请求 /api/analysis/single:
  → Redis 记录: "admin:/api/analysis/single" = 1（60秒后自动删除）
  → 1 < 限制(10次) → 放行

用户 admin 第 10 次请求:
  → Redis: "admin:/api/analysis/single" = 10
  → 10 = 限制(10次) → 放行（这是最后一次）

用户 admin 第 11 次请求:
  → Redis 返回: 11
  → 11 > 限制(10次) → 返回 429 "请求过于频繁，请稍后重试"

60 秒后，Redis 的 key 过期自动删除，计数器归零，用户又可以继续请求
```

## 6. 数据库：数据存在哪里

### 6.1 MongoDB 和 Redis 的分工

| | MongoDB | Redis |
|---|---|---|
| **存什么** | 股票数据、分析结果、用户信息、配置 | 临时任务队列、限流计数器、热点缓存 |
| **数据特点** | 持久化，重启不丢 | 内存存储，重启就没了 |
| **类比** | 仓库（存持久数据） | 桌面（放正在用的东西） |

### 6.2 MongoDB 中存了哪些集合（表）

| 集合名 | 内容 | 谁写入 |
|---|---|---|
| `stock_daily_quotes` | 股票每日行情（开高低收、成交量） | 定时同步任务 |
| `market_quotes` | 实时/近实时行情快照（前端展示用） | 定时采集任务 + 启动补数 |
| `stock_basic_info` | 股票基本信息（代码、名称、行业） | 定时同步任务 |
| `news` | 股票相关新闻 | 新闻同步任务 |
| `analysis_tasks` | 分析任务（task_id、状态、结果） | Worker |
| `users` | 用户账号信息 | 注册/登录 |
| `llm_configs` | LLM 提供商配置 | Web UI 配置管理 |
| `favorites` | 用户自选股 | 前端操作 |

### 6.3 Redis 中存了哪些数据

| Key 模式 | 内容 | 有效期 |
|---|---|---|
| `queue:analysis` | 待执行的分析任务列表 | 永久（消费后删除） |
| `rate_limit:{user}:{endpoint}` | 限流计数器 | 60 秒 |
| `daily_quota:{user}:{date}` | 每日配额计数器 | 24 小时 |
| `cache:stock:{code}` | 股票数据缓存 | 按配置 |
| `ws:connections` | WebSocket 活跃连接 | 实时 |

## 7. 任务队列：为什么分析不是"即时"的

### 7.1 问题

一次完整的 Agent 分析需要 1-3 分钟（4 个分析师 + 牛熊辩论 + 风险辩论 + 10+ 次 LLM 调用）。如果用户提交后干等，浏览器会超时（HTTP 请求通常 30 秒就断了）。

### 7.2 解决方案：异步任务队列

```
用户提交分析
    │
    ▼
路由处理器: 创建任务 → 放进 Redis 队列 → 立即返回 task_id（毫秒级）
    │
    │  用户拿到 task_id，前端显示"排队中..."
    │
    ▼
Worker: 从 Redis 队列取任务 → 调用 Agent 引擎（1-3分钟）
    │
    │  Worker 每完成一个 Agent 节点就推送进度
    │
    ▼
分析完成 → 结果写入 MongoDB → Worker 推送"完成"
    │
    ▼
前端: 收到"完成"通知 → GET /api/analysis/result/{task_id} → 展示报告
```

**关键角色**：

| 角色 | 做什么 | 运行方式 |
|---|---|---|
| **路由处理器** | 接收请求、创建任务、放进队列、返回 task_id | 同步，毫秒级 |
| **Redis 队列** | 存储待执行的任务（FIFO 先进先出） | 一直在内存里 |
| **Worker** | 从队列取任务、调 Agent 引擎、推送进度、写入结果 | 独立进程，持续运行 |

## 8. 实时推送：前端如何实时看到分析进度

### 8.1 两种方式

| 方式 | 方向 | 适用场景 |
|---|---|---|
| **SSE** (Server-Sent Events) | 服务器 → 客户端（单向） | 任务进度推送 |
| **WebSocket** | 双向通信 | 通知 + 进度推送 + 前端可发消息 |

### 8.2 SSE 的工作方式

```
前端:
  const source = new EventSource("/api/stream/progress/abc123")
  source.onmessage = (event) => {
    console.log("进度: " + event.data)  // "📊 市场分析师完成"
  }

后端:
  路由处理器返回一个"永不结束"的响应，每次有进度就写一行:
    data: {"node": "Market Analyst", "status": "completed"}

    data: {"node": "Bull Researcher", "status": "running"}

    data: {"node": "Risk Judge", "status": "completed"}
    data: [DONE]
```

### 8.3 WebSocket 的工作方式

```
前端:
```

## 9. 你学过的 Agent 引擎和后端的连接点

回顾你 Day 2-7 学的内容，它们是**在 Worker 进程中被调用的**：

```python
# app/worker/analysis_worker.py 中的核心逻辑（简化版）

from finagentlab.graph import FinAgentLabGraph

# Worker 启动时创建一次 Graph 实例
graph = FinAgentLabGraph(
    selected_analysts=["market", "fundamentals", "news", "social"],
    config=config   # 从 MongoDB 读的配置
)

# 每次拿到任务就调用
async def execute_analysis(task):
    final_state, decision = graph.propagate(
        company_name=task["symbol"],      # "000002"
        trade_date=task["trade_date"],    # "2025-07-08"
        progress_callback=send_progress   # 推送进度的回调函数
    )
    # decision = {"action": "买入", "target_price": 18.50, ...}
    return final_state, decision
```

**所以整个系统的调用链是**：

```
用户点"分析"按钮
  → 前端 POST /api/analysis/single
  → analysis.py 路由 → 创建任务 → 放进 Redis 队列 → 返回 task_id
  → Worker 从 Redis 取任务
  → Worker 调用 FinAgentLabGraph.propagate()
  → Agent 引擎运行（你 Day 2-7 学过的所有东西）
  → 分析完成 → 结果写入 MongoDB
  → Worker 通过 WebSocket 推送"完成"
  → 前端获取结果 → 展示报告
```

## 10. 总结：你不需要记住每一个文件

对于"没有后端基础但理解了 Agent 引擎"的你，只需要记住这个模型：

```
┌──────────┐     HTTP请求      ┌──────────────┐     函数调用     ┌─────────────┐
│          │ ─────────────────→│              │ ───────────────→│             │
│  浏览器   │                   │   FastAPI    │                  │ Agent 引擎  │
│  (前端)   │ ←──────────────── │   (后端)     │ ←────────────── │ (你已学过的) │
│          │     JSON响应       │              │    返回结果     │             │
└──────────┘                   └──────────────┘                 └─────────────┘
                                     │
                                     ├── MongoDB（存数据）
                                     ├── Redis（缓存+队列）
                                     └── Worker（后台执行分析）

中间件 = 请求的安检通道
路由 = URL → 函数的映射
Worker = 真正调用 Agent 引擎的地方
```
